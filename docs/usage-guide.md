# 有毒订单监控用户使用指南

版本：2026-08-14 主力行为与 Shadow 监控版

这份指南面向每天打开页面看信号、复盘事件和检查通知的人。它只讲怎么使用当前版本，不包含部署和服务器维护。

## 1. 先记住系统边界

本系统是只读监控工具：不自动交易、不下单、不撤单、不操作账户或资金。

页面里的信号首先是市场异常观察。只有证据链完整、状态为 `confirmed` 的行为，才能显示为“主力建多”或“主力建空”。普通放量、短窗口高分和清算冲击都不能单独证明主力意图。

```text
市场冲击回答：这次行情有多大？
主力行为回答：这次行情是否有足够证据指向新多、新空或其他明确行为？
方向回答：当前主动成交偏买还是偏卖？
```

这三个问题必须分开看。

## 2. 当前页面和用途

- `监控首页`：看系统健康、候选信号和整体运行边界。
- `BTC 合约监控`：看 BTC 永续主动成交、OI、价格响应、清算和主力行为证据。
- `ETH 合约监控`：使用 ETH 自己的数量单位和阈值，不套用 BTC 门槛。
- `BTC 现货监控`：看 BTC 现货主动买卖、跨交易所确认和吸收/压制。
- `ETH 现货监控`：看 ETH 现货主动流，数量均为 ETH。
- `新币合约监控`：观察新上线合约的异常流动性与候选事件。
- `山寨合约异常`：观察启用范围内的山寨永续异常；系统模式关闭时不代表故障。
- `异常信号`：查看当前候选和风险信号。
- `信号历史`：复盘已持久化的信号和通知结果。
- `告警规则`：查看规则，不代表可以直接修改生产交易行为。
- `Discord 设置`：检查通知是否配置、是否 dry-run，以及最近发送结果。
- `系统设置`：查看只读运行状态和数据源健康。

## 3. 最推荐的看盘顺序

1. 看顶部 `HEALTH`、数据源状态和数据新鲜度。数据降级时先降低信号权重。
2. 看事件方向：主动买压、主动卖压、吸收、压制或中性。
3. 看 `behaviorState`，先区分证据不足、候选、已确认和已失效。
4. 看 OI、价格响应、跨交易所确认和清算证据是否互相支持。
5. 再看市场冲击等级。冲击等级高只说明事件大，不自动等于主力确认。
6. 打开详情卡检查支持证据、反证、失效原因和数据质量。
7. 最后看 Discord 状态，确认信号是否达到对应通知通道的门槛。

## 4. 合约事件列表怎么读

合约事件流来自已持久化的历史事件，不是顶部 `latest` 快照。

- 顶部实时状态：只说明当前时刻的方向、健康和最新等级。
- 事件列表：显示最近历史事件，可用于复盘。
- `ACTIVE / CLOSED`：是事件生命周期投影，不是开仓和平仓指令。
- 页面刷新：不会删除历史事件；短暂加载中应等待后台恢复。

主要字段：

- `时间`：事件发生或最近更新的时间。
- `市场 / 事件`：币种、名义成交价值和事件类型。
- `方向`：买入、卖出、吸收、压制或不明确。
- `等级`：市场冲击等级，与主力行为可信度分开。
- `窗口总流量`：该窗口的合约成交总量。
- `净流量`：主动买入减主动卖出；正数偏买，负数偏卖。
- `真实换手`：合并窗口去重后的成交量，用于避免 5s、15s、60s 重复累计。
- `价格响应`：成交爆发后价格是否跟随、被吸收或被压制。
- `OI`：用于区分新开仓、回补、平仓和证据不足。

BTC 页面数量单位是 BTC，ETH 页面数量单位是 ETH。不要直接比较两个页面上的绝对数量。

## 5. 主力行为状态怎么读

`behaviorState` 是当前版本判断主力行为的权威状态。

### insufficient / 证据不足

只观察到成交异常，或 OI、价格、数据质量、跨交易所确认不足。

这时页面应显示“主动买压”“主动卖压”或普通冲击，不应显示“主力建多/主力建空”。

### provisional / 候选

部分证据已经匹配，但仍缺少更长窗口、现货配合或持续价格响应。

常见候选：

- 空头回补
- 多头平仓
- 下方吸收
- 上方压制
- 清算驱动

候选状态值得观察，但不是主力确认。

### confirmed / 已确认

只有在 OI、价格响应、方向占比、跨交易所确认和数据质量同时满足时，系统才会确认主力行为。

当前确认门槛的关键条件包括：

```text
dataQuality >= 70
方向占比 >= 55%
跨交易所方向确认
OI 证据可用且未降级
价格同向变化绝对值 >= 0.12%
行为状态 = confirmed
行为置信度 >= 80 才能进入主力行为通知通道
```

已确认的主要类型：

- `new_long_build`：主动买入 + OI 上升 + 价格跟随，显示“主力建多”。
- `new_short_build`：主动卖出 + OI 上升 + 价格跟随，显示“主力建空”。

### invalidated / 已失效

之前确认过，但后续 OI、价格或数据质量不再支持原结论。

已失效不是系统报错，而是证据状态发生变化。详情卡会显示失效原因和反证，使用时应停止沿用原确认结论。

## 6. 常见行为类型怎么理解

### 主力建多

主动买入、OI 上升、价格上行并获得多源确认。它代表新多头建仓概率较高，不代表价格不会回调。

### 主力建空

主动卖出、OI 上升、价格下行并获得多源确认。它代表新空头建仓概率较高，不代表可以直接追空。

### 空头回补

主动买入但 OI 下降，更像空头平仓推动上涨，不等于新多建仓。

### 多头平仓

主动卖出但 OI 下降，更像多头离场推动下跌，不等于新空建仓。

### 下方吸收

卖压很大但价格没有有效下行，说明下方存在承接。它是候选结构，需要更长窗口和现货证据确认。

### 上方压制

买压很大但价格没有有效上行，说明上方存在卖盘。它是候选结构，不等于价格立即下跌。

### 清算驱动

行情主要由强平和被迫成交推动。清算事件走独立的市场冲击通知通道，不会被描述为主力主动建仓。

## 7. 市场冲击等级怎么读

`severity` 和 `impactLevel` 主要描述事件规模、稀有度、价格冲击和多源确认。

- `Calm / C`：普通或低冲击事件。
- `Medium / B`：有一定影响，值得保留观察。
- `High / A`：明显市场冲击，需要结合行为证据复核。
- `Critical / S`：极端影响候选；当前版本只有可复核的实时大清算或特大跨所换手才保留为 S。

重要规则：

```text
S 级市场冲击 ≠ 主力确认
confirmed 主力行为 ≠ 一定是 S 级行情
```

普通大额成交即使历史等级很高，只要行为证据不足，仍应显示为主动买压、主动卖压或市场冲击。

S 级硬证据至少满足其一：

```text
实时清算总量 >= 2,500 BTC；或
总成交 >= 20,000 BTC 且窗口 >= 60s、跨所确认、动态倍数 >= 10、历史分位 >= 99.5、方向占比 >= 65%
```

原始评分仍保留在诊断字段中，但不再把普通高分事件直接展示为 S，也不会仅凭 S 候选触发 Discord。

## 8. Shadow 候选通道怎么读

Shadow 是独立于 Impact 和 Behavior 的“持续主动成交痕迹”观察通道，用来捕捉单窗未过 High 门槛、但在 15 分钟到 1 小时内持续同向的流量。它不是“主力买卖”结论，也不会触发下单。

状态按证据累积变化：

- `suspect`：首次出现持续、方向占比高于 55% 的子 High 流量。
- `watching`：至少连续两个相邻窗口，且成交质量合格。
- `corroborated`：至少三个连续窗口，同时 OI 可用、跨交易所确认、价格效率偏低；仍然只是候选痕迹。
- `invalidated`：出现大脉冲、实时清算、数据质量不足或窗口间断过久。

只读接口：

```text
GET /api/contract-whale/shadows?symbol=BTC&lookbackMin=60&limit=50
```

返回会明确标记 `lane=shadow`、`readOnly=true` 和 `executionEnabled=false`。Shadow 默认观察，不进入 Impact Discord 通知，也不能替代 OI、价格和现货证据。

## 9. 详情卡怎么用

点击事件后，优先看以下区域：

1. `行为状态`：是否 confirmed，还是 provisional / insufficient / invalidated。
2. `支持证据`：OI、价格跟随、跨市场方向确认等。
3. `反证`：OI 下降、价格不跟随、现货不确认或数据降级等。
4. `行为置信度`：主力行为证据强度，不等于市场冲击等级。
5. `市场冲击`：事件规模和极端程度。
6. `数据质量`：来源覆盖、延迟、warmup 和证据新鲜度。
7. `合并来源`：同一事件跨 5s、15s、60s 窗口的去重聚合情况。
8. `Discord gate`：是否符合通知要求、是否已发送，以及未发送原因。

如果详情很长，应以状态、支持证据、反证和失效原因为主，不要只看顶部等级。

## 10. 现货监控怎么读

现货监控用于确认真实现货买卖是否配合合约异动。

常见类型：

- 现货主动买入
- 现货主动卖出
- 下方吸收
- 上方压制
- 交易所价格或流向差异

推荐组合判断：

```text
合约强 + 现货同向 + OI 同向 + 价格跟随 = 主力行为证据更完整
合约强 + 现货不确认 = 更像合约冲击、回补或清算
现货强 + 合约较弱 = 可能是现货吸筹/派发，继续等待合约和价格确认
```

BTC 和 ETH 使用不同的净流量门槛。ETH 的数量必须按 ETH 解读，不能把 1000 ETH 当成 1000 BTC。

## 11. BTC 1H 主动成交差值提醒

当该功能启用时，系统只使用已经收线的 Binance `BTCUSDT` 永续 1 小时 K 线主动成交数据，不使用尚未收盘的小时。

```text
Delta = 主动买入 BTC - 主动卖出 BTC
|Delta| > 1000 BTC 才进入提醒候选
Delta > 0：偏多主动成交
Delta < 0：偏空主动成交
```

这条提醒描述的是 1 小时主动成交差，不是资金净流入、持仓变化或独立买卖建议。

通知中应同时显示主动买入、主动卖出、净差、买卖占比、周期和“1H 已收线”。系统使用持久化 outbox 重试并去重，同一根已收线 K 线不会反复推送。

## 12. Discord 通知怎么理解

当前通知分为独立通道，不能混读。

### 主力行为通知

必须满足：

```text
behaviorState = confirmed
mainForceConfirmed = true
behaviorConfidence >= 80
数据质量和通知公共门槛通过
```

通知会明确写“主力建多”或“主力建空”，并带方向颜色和关键证据。

### 市场冲击 / 清算通知

用于极端成交、清算和市场影响事件。即使允许推送，文案也应写“市场冲击”或“清算驱动”，不会冒充主力确认。

### 1H 主动成交差通知

只针对已收线小时，阈值为 `|Delta| > 1000 BTC`。它与合约事件流使用独立去重和重试记录。

### 常见状态

- `sent`：Discord 接受成功。
- `pending / retry / sending`：正在 outbox 中等待或重试，保留策略不会删除对应事件。
- `dry_run / would_send`：通过门槛但只模拟，没有真实发送。
- `webhook_missing / not_configured`：没有可用 webhook。
- `suppressed`：未达到通知门槛。
- `behavior_not_confirmed`：市场可能很大，但主力行为证据不足。
- `send_failed`：发送失败，需结合重试次数和服务器网络检查。

## 12. 数据保留规则

当前合约和现货信号统一使用三档保留，不再把普通高分信号永久保存。

```text
ordinary / 普通：7 天
important / 重要：30 天
critical / 关键：365 天
```

合约关键数据通常要求极端且可复核的证据，例如极端 60 秒换手并获得多交易所确认，或非常大的清算量。普通 S 形候选不会因为等级文字就自动保存一年。

现货重要和关键门槛按币种单位计算：

- BTC：净流量绝对值达到 100 BTC 进入重要档，达到 500 BTC 进入关键档。
- ETH：净流量绝对值达到 1000 ETH 进入重要档，达到 5000 ETH 进入关键档。
- 已发送通知、多交易所确认或已确认行为至少进入重要档。

待发送、重试中或发送中的通知关联事件不会被清理。删除采用后台分批执行；数据库文件不会因为删除记录立即缩小，物理空间回收需要单独维护窗口。

## 13. 数据质量和异常提示

### `N/A`、`UNKNOWN` 或数据暂不可用

说明某个数据源、快照或分析结果尚未恢复。页面可能保留上一次结果，但不能把旧结果当成当前实时状态。

### 页面显示加载中

刷新后前端会先显示壳和缓存，再等待后端事件流。短暂 loading 不代表事件被删除。

### OI 不可用或降级

行为判断会 fail-closed：不会确认主力建多或建空。

### OKX disabled

当前配置未启用 OKX 时，它不参与总成交量、交易所数量或数据质量扣分。disabled 不等于断线故障。

### 页面能打开但 Discord 没有消息

依次检查：

1. 信号是否进入正确通知通道。
2. 行为是否 confirmed，或是否属于清算/冲击通道。
3. 当前是否 dry-run。
4. outbox 是否 pending / retry。
5. webhook 是否配置。
6. 服务器访问 Discord 是否被网络阻断。

## 14. 最容易误读的场景

### 大额主动买入就是主力建多

不对。还需要 OI 上升、价格跟随、多源确认和健康数据。

### 大额主动卖出就是主力建空

不对。OI 下降时可能是多头平仓，价格跌不动时可能是下方吸收。

### S 级一定会发主力通知

不对。S 是市场冲击维度；主力通知必须通过 behavior confirmed gate。

### 清算很大就是主力砸盘或拉盘

不对。清算是被迫交易，走独立冲击通道。

### 页面显示 0 条就是系统没有工作

不一定。可能是当前事件低于可见门槛、筛选条件过严、数据 warmup，或暂时没有历史事件进入该视图。

### 事件从 confirmed 变成 invalidated 是系统反复横跳

不对。当前版本允许后续证据撤销旧确认，这是为了防止错误结论永久锁存。

## 15. 日常使用清单

1. 确认页面显示 `READ ONLY`，运行边界正常。
2. 检查 BTC/ETH 对应数据源健康和更新时间。
3. 先看方向，再看行为状态。
4. 只有 confirmed 才使用“主力建多/建空”的解释。
5. 打开详情卡核对支持证据和反证。
6. 将清算、回补、平仓与新开仓分开。
7. 用现货确认合约方向，不只看单一交易所或单一窗口。
8. 检查 Discord 是 sent、dry-run、suppressed 还是 retry。
9. 复盘时结合事件生命周期和后续价格，不用单条信号做结论。

最重要的一句话：

```text
先判断证据是否完整，再判断方向；先区分主动行为和被迫交易，再决定这条信号值不值得跟踪。
```
